PART 1 · 自动化 PIPELINE

全球 50 大区礼物资产 AI 自动化生产管线

业务背景：下月初上线面向全球 50 个不同文化大区的专属礼物资产。沿用传统产研流程将产生极高外包与沟通成本。以下方案以「多 Agent 协作 + 强制 JSON 协议 + 断路器止损」构建可规模化的 AI 生产管线，目标是把「一次艺术创作」降维成「可并行的结构化生成」。

设计基调：这套管线不是「把图丢给一个大模型」，而是把「一个能干的艺术家」拆成「一组各司其职、用机器可读协议交接、互相质检的工种」。核心矛盾是质量审查必须发生在生成链路内部，而不是靠人最后看一眼。

一、架构设计：多 Agent 流水线

三个验收项分别落在：管线拓扑（§1）→ 单点提示词（§2）→ 全局熔断（§3）。它们不是三个独立文档，而是同一套系统的三层纵深防御。

1.1 管线拓扑总览

AGENT-0区域需求解析
入: 50 大区清单 + 文化档案
出: 结构化规格 spec.json
→
AGENT-1文化合规审查
入: spec.json
出: 合规判定 + 禁项清单
→
AGENT-2礼物概念生成
入: 合规 spec
出: concept.json（构图/描述/参考）
→
AGENT-3材质贴图生成
入: concept.json
出: 贴图资产 asset/
→
AGENT-4结构校验
入: 贴图 + concept
出: pass / 重试 / 拒绝
→
AGENT-5打包交付
入: 通过资产
出: 分区礼包 bundle/

其中 AGENT-0/1/4 是「把关者」（gatekeeper），AGENT-2/3 是「生产者」（producer），AGENT-5 是纯装配。把关者不生产内容，只做结构化判定 —— 这是把「人肉质检」前置进管线的关键。

1.2 核心 Agent 职责与数据流

Agent输入处理输出失败路径
0 需求解析50 大区文化档案、礼物品类、预算把自然语言需求解析为结构化规格，拆出「文化符号库」「禁用列表」「目标画风」spec.json（每大区一份，机器可读）解析置信度低 → 挂起人工确认，不硬猜
1 文化合规审查spec.json对每个候选礼物元素做合规评分：宗教禁忌 / 政治符号 / 颜色禁忌 / 手势含义 / 数字禁忌，输出「通过 / 需改造 / 禁止」三态合规判定 + 每项原因 + 建议替换符号任一「禁止」→ 该元素直接从候选池移除，不再进入生成
2 概念生成合规后的 spec生成构图概念：主体、视角、光影、文案、画面描述（JSON，非自由文本）concept.json + 供 3 用的结构化绘画指令生成含违禁物 → 触发 §2 的异常重试规则
3 贴图生成concept.json调图像模型产出贴图资产，按 concept 的分层（主体/背景/光效）分通道生成PNG 贴图 + 元数据 meta.json（尺寸、通道、seed）贴图尺寸/格式不符 → 重绘，重试上限 3 次
4 结构校验贴图 + concept + 合规清单自动化检测：分辨率、透明度、破边、主体遮挡、文字可读性、是否含禁项残留；并对齐 concept 的构图要求pass / retry / reject + 具体失败点retry → 带失败原因回注概念层；reject → 终止并告警
5 打包交付全部通过资产按大区打包、生成 manifest、做 CDN 命名与版本化bundle/ + 校验和缺失文件 → 拒绝打包，整批回查

1.3 质量审查的拦截机制

拦截不是「最后一道门」，而是分布在 3 个层级，任何一层失败都不会把残次品放出管线：

  1. 前置拦截（AGENT-1 合规层）：文化合规在进入生成之前完成，违禁元素根本不进候选池。这是最省算力的一层 —— 拦截发生在生成前，而不是生成后丢弃。
  2. 契约拦截（AGENT-2/3 协议层）：生产者必须输出严格 JSON（§2 的 schema），任何结构不符 / 字段缺失 / 越界值都会在进入下一阶段前被 schema 校验拒掉。校验失败即重试，不产生半成品。
  3. 证据拦截（AGENT-4 证据层）：对成图做可观察的像素级 / 结构级检测（文字可读性、破边、禁项残留、主体对齐），只有拿到「可见证据」才放行 —— 与 Part 3 的「评分必须以可观察依据支撑」是同一套哲学。
数据流真相：所有 Agent 之间传递的是 结构化 JSON / 文件路径，绝不传自由文本。自由文本是人类协作的介质，却是机器管线里的「协议污染源」——一个 Agent 的「感觉」无法被下一个 Agent 的「断言」校验。强制 JSON 是整条管线可测试、可回溯、可熔断的前提。

二、上下文工程：生成 Agent 核心提示词

以下提示词作用于 AGENT-2（礼物概念生成）——管线里最「自由」也最需要被约束的生产者。它通过三段机制实现「既要创造力、又要机器可读、又要安全兜底」：

2.1 系统提示词（可直接粘贴）

// ============ SYSTEM PROMPT · AGENT-2 礼物概念生成 ============
你是「礼物概念生成 Agent」。你的唯一产出是符合下方 JSON Schema 的调用指令。
你禁止输出任何非 JSON 内容（禁止 Markdown、禁止解释、禁止寒暄、禁止 ``` 包裹）。

【角色边界】
- 你的上游输入是 AGENT-1 已通过合规审查的 spec.json，其中已列出该大区允许符号与禁用符号。
- 你只负责「概念层」，不生成最终图片；你的输出会被下游贴图 Agent 执行。

【输出协议】必须严格输出以下 JSON（字段一个不少，缺失即视为无效）：
{
  "intent": "concept",            // 固定值
  "region": string,               // 大区标识，取自 spec.region
  "concept": {
    "subject": string,            // 主体描述（<30字）
    "viewpoint": string,          // 视角，仅取枚举: 正面/侧面/俯视/仰视/特写
    "lighting": string,           // 光影，仅取枚举: 顶光/侧光/暖光/冷光/逆光
    "palette": [string],          // 主色数组（3-5 个 hex）
    "composition": string,        // 构图要点
    "scene": string               // 场景/背景描述
  },
  "refSymbols": [string],         // 引用的合规符号，全部须在 spec.allowed 内
  "styleRef": string,             // 画风参考（可空字符串）
  "safety": {
    "checked": true,
    "bannedTouched": false,
    "note": string                // 说明为何确认未触碰禁用项
  }
}

【硬性约束】
1. refSymbols 的每一项都必须在 spec.allowed 中逐字存在；引用到任何 spec.banned 中的符号，该 JSON 直接判为无效。
2. palette 必须规避 spec.colorTaboo 列出的颜色区间。
3. 你的输出会被 schema 校验器逐字段检查，任何「想象出来的新字段」都会被拒。

【宗教违规处理与重试规则】（最高优先级）
- 场景 A · 模型试图生成特定宗教违规符号（如某宗教的神像、圣器、经文、专属图腾被作为主体或装饰）：
  1) 立即终止当前概念，不要尝试「把违规符号画得隐晦」。
  2) 输出一次重试：把 refSymbols 替换为 spec.allowed 中的中性替代符号（如几何图案 / 自然元素 / 非宗教文化纹样）。
  3) 在 safety.bannedTouched 置 true，safety.note 写明「检测到违规符号 X，已替换为中性符号 Y」，并显式附上重试标记 "retry": true。
  4) 重试仍命中违规 → "retry": true 且 "safety.bannedTouched" 保持 true，连续 3 次后必须输出 {"intent":"give_up","reason":"..."}，把问题抛回 AGENT-1 重新评估该区域符号库，禁止无限自旋。
- 场景 B · 你不确定某符号是否违规：默认按「疑似违规」处理，走与 A 相同的替换流程，而不是冒险保留。宁可保守，不可越界。

【自检清单】（输出前逐条在内心核对，不输出）
- refSymbols ⊆ spec.allowed ✓
- palette 未触碰 colorTaboo ✓
- 无任何宗教/政治/敏感符号残留 ✓
- 字段与枚举完全符合 schema ✓

2.2 提示词设计要点拆解

机制作用为什么必要
「只输出 JSON」+ 枚举白名单从结构上杜绝自由文本自由文本无法被下游 schema 校验，是管线污染源；枚举把「想象力」约束在可判定的有限集内
safety.checked/bannedTouched 强制字段把「安全自检」变成硬性协议而非自觉不显式要求，模型往往省略安全声明；强制字段让每一条输出都自带「安全审计记录」
场景 A 的「替换 → 标记 → 重试上限 → give_up」链把宗教违规处理做成有终点的重试协议避免「违规就无限重试」变成另一种死循环；给出明确的退出路径（give_up 抛回上游）
retry 标记 + bannedTouched 双信号让下游能区分「正常输出」与「违规后修正」便于审计与统计：可以量化每条资产是否踩过雷，反哺 AGENT-1 的合规清单

三、保险机制：死循环断路器与止损

场景：管线在处理某个极小语种国家的资产时陷入死循环 —— 模型不断生成逻辑冲突的几何体，算力持续空转。作为系统设计者，你需要可量化的「触发条件」和自动「止损」。

3.1 断路器触发条件（Circuit Breaker Trip）

断路器不是「感觉卡住了」，而是监控 4 个可观测信号，任一达到阈值即熔断：

信号度量方式触发阈值含义
重试死循环同一资产的 retry 计数≥ 5 次模型在同一资产上反复失败，说明 concept 本身不可生成，重试无意义
几何自冲突结构校验 Agent 返回「几何自矛盾」错误的次数连续 ≥ 3 次同一失败类别反复出现 = 输入规格有系统性 bug，不是偶发
算力空转同一资产累计生成耗时的移动平均超过该资产预估成本 × 6超出成本红线，继续烧钱不值得
错误收敛率连续 N 次重试的成功率最近 10 次重试成功率 = 0零成功说明模型进入「越改越错」的退化态

3.2 熔断后的自动止损（Breaker Actions）

  1. 冻结该资产：立即停止该资产的生成任务，释放占用的 GPU 实例 / API 并发，停止继续计费。
  2. 自动降级（fallback）：将该资产降级为「模板化生成」——用预置的通用礼物模板 + 该大区仅剩的合规符号，产出保底版本，保证该大区不出现空档（上线不缺席）。
  3. 根因隔离（backoff + 隔离）：把失败资产连同 5 次重试的完整日志（输入 spec、每次的 concept、校验错误）归档，标记为「需人工介入」；同时把该大区标记为 circuit_open，不再自动触发新的生成，防止同类资产继续烧算力。
  4. 指数退避重试窗口：断路器打开后进入冷却（初始 5 分钟，指数翻倍至上限 30 分钟），冷却期间拒绝该资产的新任务；冷却结束后只允许「带修复补丁」的任务重新进入（修复补丁来自根因分析，而非盲目重试）。
  5. 告警升级：熔断事件写审计日志 + 推送告警到值班人，附上「为什么熔断」的机器可读摘要，人工可在 UI 上决定「永久拒绝 / 修复后放行 / 手动注入替换符号」。

3.3 断路器状态机

状态进入条件行为退出条件
CLOSED（正常）初始 / 冷却后通过正常生成，统计失败信号任一信号达阈值 → OPEN
OPEN（熔断）信号达阈值拒绝新任务，冻结算力，触发 fallback + 告警冷却结束（指数退避到期）→ HALF-OPEN
HALF-OPEN（试探）冷却结束只允许 1 个「带修复补丁」的试探任务试探成功 → CLOSED；失败 → 回 OPEN（并再次拉长冷却）
PERMANENT（永久拒绝）HALF-OPEN 连续失败 2 次 / 人工决定永久标记该资产不可自动生成，仅保留人工通道仅人工手动重置
为什么这样设计（设计意图）：真正的风险不是「偶发失败」，而是「同一个坏输入反复触发同一类失败」——这几乎总是输入规格或符号库的问题，而不是模型偶发。所以断路器核心不是「检测失败」，而是检测「重复失败的模式」并斩断它：一旦判断为系统性问题，就停止烧算力，转为降级保底 + 人工根因分析，让 49 个大区不受影响，也让这个「难搞的大区」不至于拖垮整批上线。
与全局设计的一致性：断路器是 §1 三层拦截之上的「第四层——运行时熔断」。前三层拦截内容（不该生成的别生成），第四层拦截行为（生成不下去时别硬烧）。三者配合：合规层管「能不能做」、协议层管「做出来对不对」、证据层管「做出来好不好」、断路器管「做不动时怎么办」——完整覆盖了规模化 AI 生产的四个失败维度。
