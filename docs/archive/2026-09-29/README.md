# Smile to Rain · Laugh to Fireworks

> AR 表情互动原型：摄像头实时识别表情 —— **微笑时屏幕下雨，大笑时烟花炸开**，
> 且烟花/雨滴粒子会与用户**头部发生真实物理碰撞反弹**。

## 1. 交互定义（把 PM 的模糊创意翻译成可验收的工程规格）

| PM 的原话 | 工程化定义 | 判定信号 |
| --- | --- | --- |
| 用户微笑 | 屏幕下雨，雨量随微笑强度连续变化 | `(mouthSmileLeft + mouthSmileRight) / 2` |
| 大笑 | 烟花爆开，持续大笑时按节奏追加连击 | `jawOpen × (0.45 + 0.55 × smile)` |
| 与头部物理碰撞 | 粒子撞到头部椭圆后按法线弹性反弹 | 478 点人脸网格拟合的头部椭圆 |

**为什么大笑不是只看 `jawOpen`**：只张嘴可能是说话、打哈欠、唱歌。
因此大笑判定强制要求「**张嘴 × 嘴角上扬**」同时成立，这是把误触发率压下来的关键一步。

**为什么不能只做阈值判定**：每个人的静息表情值不同 —— 有人自然状态 `mouthSmile` 就有 0.22，
有人全力笑也只到 0.45。固定阈值必然两头不讨好。因此启动后先做 0.9s 基线采集，
阈值作用于**归一化后**的值（`Baseline` 快速下修、缓慢上修，始终贴着「这个人不笑时的值」）。

## 2. 架构

```
camera ──► FaceLandmarker (WASM/GPU, 一次推理)
              │  ├─ 52 维 blendshape ──► ExpressionFSM ──► NEUTRAL / SMILE / LAUGH
              │  │                          │
              │  │                          ├─► RainField      (雨量 = 微笑强度, GPU)
              │  │                          └─► SparkPool      (大笑 burst + 微笑嘴角流, GPU)
              │  └─ 478 点 face mesh ──► fitHeadEllipse ──► 头部椭圆
              │                                                   │
              └─► PerfMonitor (fps → 质量档位)                     ▼
                                              WebGL2 合成着色器 (headDist 边界穿越碰撞)
                                                          │
                                              WebGL2 不可用 ──► Canvas2D 降级渲染器
```

**核心：一次推理同时供表情判定与碰撞体使用**，不叠加第二个人脸模型，这是 ROI 的底线。

## 3. 性能策略（性能红线）

### 3.1 粒子物理 100% 在 GPU

粒子状态打包进**两张 RGBA16F 浮点纹理**（`pos.xy/vel.xy` + `life/maxLife/hue/seed`），
用 **ping-pong FBO + MRT** 在 fragment shader 内完成全部模拟。

| | Canvas2D 时代 | 现在（WebGL2） |
| --- | --- | --- |
| 粒子容量 | 数百级 | **65,536**（HIGH 档 256×256） |
| CPU 每帧开销 | 遍历更新全部粒子 + 碰撞判定 | 约 10 个 uniform + 1 张摄像头纹理 |
| 每帧绘制调用 | 上千次 | **9 次**（模拟 1 + 雨 1 + 火花 1 + 辉光 5 + 合成 1） |

### 3.2 其余手段

| 手段 | 解决的问题 |
| --- | --- |
| 火花绘制按**活跃高水位裁剪** | 空闲期不对整池 6.5 万粒子跑顶点着色器 |
| 人脸推理**隔帧执行**（`detectEvery`） | 低端机省一半推理算力 |
| `PerfMonitor` 三档自适应降级 | 低端机掉帧时自动收紧粒子容量 / DPR / 推理频率 |
| 镜头震动走**着色器 uv 偏移** | 不改 canvas 尺寸、不触发 layout，零重排 |
| 摄像头层**原样直通，不参与任何调色** | 省掉整段调色算术，且人脸不会被链路拖灰（见 §5） |
| 美颜**默认关闭**（可按需开启） | 关闭时 `smoothSkin` 在 `uBeauty<=0.001` 处提前 return，零纹理采样 |
| 飘心节点**预建复用** | 运行期零 `createElement` |
| HUD DOM 写入选在 ~8Hz 节流 | 逐帧写 DOM 会触发样式重算，粒子满负载时吃掉 3–5ms |
| 页面隐藏即停推理与物理 | 后台偷跑耗电 |
| `video.currentTime` 未变则跳过推理 | 静止画面空转算力归零 |

**质量档位表**（`src/glRenderer.js`，滞后阈值 46/56 fps + 2.5s 冷却，避免画质抽搐）：

| Level | 粒子容量 | 雨槽位占比 | 推理频率 | 渲染 DPR |
| --- | --- | --- | --- | --- |
| HIGH | 65536 | 0.075 | 每帧 | ≤1.5 |
| MID | 25600 | 0.080 | 每帧 | ≤1.25 |
| LOW | 9216 | 0.090 | 隔帧 | 1.0 |

### 3.3 Canvas2D 降级路径

WebGL2 或浮点渲染目标不可用时自动切换（约占极少数老旧设备），对外接口与 `GLRenderer`
**完全一致**，`main.js` 无需任何分支判断。该路径使用 `Float32Array` SoA 粒子池 +
空闲索引栈（运行期零分配）、启动时烘焙 16 张色相 sprite、雨滴/拖尾各合并为一次
`beginPath + stroke`。

## 4. 表情状态机的三重抗抖动

1. **EMA 平滑**：单帧模型输出噪声大，直接阈值会让特效闪烁；平滑系数（0.30）做了帧率无关处理。
2. **迟滞（hysteresis）**：进入阈值 > 退出阈值，防止临界点反复横跳（微笑 0.20/0.11，大笑 0.30/0.17）。
3. **连续帧确认**：进入需连续 2 帧，退出需连续 9 帧 —— 退出比进入更「粘」，否则雨会断断续续地下。

触发节奏：校准 0.9s，burst 冷却 0.38s，持续大笑每 0.52s 追加一发（连击）。

## 5. 直播特效语言（视觉层）

| 特征 | 实现 |
| --- | --- |
| **人保持原样** | 摄像头层**不做任何调色**，逐位直通。见下方「为什么关掉美颜」 |
| **背景退后** | 只对脸部椭圆之外做去饱和 + 压暗（借鉴 AR 滤镜的 face-oval clip 思路），人脸像素一个不动 |
| **烟花在空域炸开** | 爆炸中心在面部前方空域（由头心→口部方向外推），**不在嘴上**。见 §5.2 |
| **异质星花型** | 牡丹型 + 垂柳型混装（垂柳占比 30%），两类星的重力/阻力/拖尾长度不同 |
| **连击递进** | 连续大笑累加 combo（3.2s 窗口清零），规模/闪光/震动/辉光/烟火半径全随连击递增，8 连封顶 |
| **多段节奏** | 0.00s 主角 → 0.15s 余爆 → 0.30s 金粉；连击 ≥3 追加 0.46s 第四段 |
| **镜头震动** | 衰减正弦（非随机抖，随机抖看着像掉帧），幅度随连击递增并有硬顶 |
| **礼物横幅** | 图标 + 礼物名 + `xN` 连击数字弹跳，三档热度配色随连击升级 |
| **直播间 UI** | 主播卡（头像圈 + LIVE 脉冲徽章 + 在线人数）、观众头像堆叠、飘心流、底部假评论框 + 圆形礼物按钮 |
| **雨势可持久** | 雨量走非对称包络：起雨半衰 0.18s（跟得上表情），收雨半衰 1.35s（雨幕慢慢收）；雨槽位占粒子袋 20%，约 1.3 万滴 |

### 5.1 为什么关掉美颜（实测数据）

首版按「短视频平台美颜」的思路做了一套组合拳：5-tap 磨皮 + 提亮 + 暖肤 + 增饱和 + 柔光叠加。
实测这五连把**中间调整体抬高约 0.21**，同时把对比度压低，人脸呈灰蒙发糊的塑料感：

| 输入 | 首版管线输出 | 原样直通 |
| --- | --- | --- |
| 中性灰 `[0.500, 0.500, 0.500]` | `[0.640, 0.627, 0.616]`（+0.21） | `[0.415, 0.415, 0.415]` |
| 室内暖光肤色 `[0.62, 0.47, 0.40]` | `[0.699, 0.607, 0.541]`（+0.21） | `[0.515, 0.390, 0.332]` |

两个根因：

1. **磨皮无差别作用**。5-tap 均值无法区分皮肤与背景，是整幅画面一起被糊。
   平台美颜自然，是因为它基于皮肤分割做局部处理 —— 这个成本不该由特效原型承担。
2. **tonemap 放错了位置**。ACES 近似是「抬暗部、压高光」的曲线
   （`filmic(0.1)=0.126`、`filmic(0.2)=0.30`、`filmic(1.0)=0.804`），
   放在整幅画面上等于把暗部提起来 → 灰蒙；同时把烟花峰值压到 0.81，
   粒子永远到不了白热 → 看着不亮。

**修正**：摄像头层直通；发光层单独做滚降，且只作用在 1.0 以上
（`e/(1+max(0,e-1)*0.25)`，1.0 以下严格是线性 1:1）。修正后实测烟花峰值恢复到 `255`（白热）。

美颜没有删除 —— 保留为 `smoothSkin` + 性能面板里的开关，默认关。
关闭时该函数在 `amount <= 0.001` 处直接 return，不产生任何纹理采样开销。

### 5.2 烟花形态：三个被实测证伪的参数

首版烟花的初速、重力、发射点三个参数都是"凭感觉"填的，实测全部偏离：

**① 初速过大 → 花型跑到屏幕外**

球壳投影的视觉特征是**边缘最密最亮**（`|v|` 自带 `sin(θ)` 分布，中心稀疏边缘密集）。
初速决定烟火半径，首版 `900~1240 px/s` 对应半径 `600~700px` —— 在 390px 宽的手机上
**边缘全在屏幕外**，用户只看到中心稀疏的几粒。这是"不像烟花"的首要原因。

离线扫描标定（复刻 `SIMULATE_FS` 积分，扫 `v0` 得到半径）：

| v0 (px/s) | 水平半径 | 占屏宽 |
| --- | --- | --- |
| 300 | 290px | 74% |
| **380** | **274px** | **70%** |
| 500 | 382px | 98% |
| 900（首版） | 603px | 155% ❌ |
| 1070（首版） | 703px | 180% ❌ |

改为 `380~510 px/s`，实测花型半径 148~253px，完整落在画面内。

**② 垂柳星重力过大 → 整片掉出画面**

垂柳星靠"垂落的金丝"建立花型辨识度，但首版 `grav=1180 / drag=0.42` 在 1.8s 生命内
下坠 **1837px**（屏幕才 844px）—— 柳星全部飞出去，等于没有。

| grav | drag | 1.8s 下坠 | 评价 |
| --- | --- | --- | --- |
| 1180 | 0.42 | 1837px | 掉出画面 ❌（首版） |
| 700 | 0.8 | 993px | 掉出画面 |
| **420** | **1.2** | **569px** | **OK**（能读成垂落，不出屏） |

**③ 光尘用统一重力 → 实际在下坠**

微笑时上浮的光尘，首版给了 40px/s 初速但沿用统一重力 `760px/s²`。
实测：**1.4s 只上升 1px**，末端 y=1020（屏幕外）—— 它其实一直在往下掉，
所以看起来像"从嘴里漏东西"。修正为负重力 + 高阻力（`grav=-140 / drag=1.2`），
实测 2.08s 上升 185px，才真正是"浮起的金尘"。

**④ 发射点在嘴上 → 读成"吐东西"**

真实烟花的前提是**在空旷处炸开**，观者在下方仰视。把发射源钉在嘴上，
视觉上必然读成"从嘴里吐出东西"。现改为：沿「头心 → 口部」方向继续外推，
落在面部前方的空域（外推量随头部尺寸缩放，并夹在画面安全区内）；
口部只保留缓慢上浮的光尘，作为"笑"与"特效"的轻量绑定信号。

**⑤ 花型随屏幕等比缩放**

上述数值都在 390×844 手机竖屏标定（`uPhysScale ≈ 1`），再由 `uPhysScale = 短边/390`
等比放大。实测三种尺寸的花型半径占短边比例：

| 屏幕 | 花型半径 | 占短边 |
| --- | --- | --- |
| 320×568 | 204px | 64% |
| 390×844 | 242px | 62% |
| 768×1024 | 455px | 59% |

**⑥ 三类粒子共用一个纹理通道**

`state1` 只有 4 个通道且已被 `life/maxLife/hue/seed` 占满。解法是让三类的
**寿命区间互不相交**（普通星 `[0.50,0.95]` / 垂柳星 `[1.15,1.65]` / 光尘 `[1.85,2.30]`），
再用 `seed` 的符号位携带垂柳标记 —— 于是无需新增通道，就能在物理与着色阶段
给三类粒子不同的重力、阻力、点尺寸与拖尾长度。

### 5.3 脸部"错位"的真正原因：合成阶段漏了一次 y 翻转

现象是**特效和人脸的垂直方向对不上**：雨会对，但辉光环和背景暗化区域整体跑到了脸的另一侧。
定位过程值得记一笔，因为这只 bug 完全隐藏在一次"看起来正常"的翻转里。

链路事实：

1. 全屏三角的顶点着色器是 `vUv = aPos * 0.5 + 0.5`，而 NDC 的 y 轴向上
   → **`vUv.y = 0` 是屏幕底部**、`vUv.y = 1` 是屏幕顶部，与 CSS 的 y 方向相反。
2. 摄像头画面看起来方向正确，是因为上传时开了 `UNPACK_FLIP_Y_WEBGL = true`，
   由纹理层又翻了一次，两次翻转刚好抵消 —— 于是**没人会怀疑这个坐标**。
3. 但 `uHead`（头部椭圆）、`uShock`（冲击波）是 CPU 侧按 CSS 坐标算好传进来的，
   直接和 `vUv * uScreen` 比对，就相当于在 y 镜像的世界里做判定：
   脸在屏幕上三分之二处，环却画在三分之一处。
4. 粒子没暴露这个问题，因为 `SPARK_VS` / `RAIN_VS` 在写 `gl_Position` 时
   都显式写了 `-ndc.y`，把翻转补回去了 —— 合成阶段漏了这一步。

修正：合成着色器统一用 `vec2 px = vec2(vUv.x, 1.0 - vUv.y) * uScreen;`。

验证（四象限定位图 + 白点标定，`readPixels` 读回）：

| 检查项 | 结果 |
| --- | --- |
| `mapX/mapY` 与着色器采样是否互为逆运算 | 预测 `[195, 211]`，实测 `[194.7, 210.7]`，**偏差 0.3px** |
| 头部椭圆中心对齐（y=150/300/500/700） | 环中心与传入值偏差 **-0.3px** |
| 冲击波环中心（y=200, r=180） | 实测中心 y=200，半径 194px |

> 顺带记个教训：定位这类问题时用「四象限彩色图 + 已知点标定 + 读回像素」比截图肉眼判断快得多，
> 截图在自动化环境里还容易超时。上面所有数字都是脚本读回的真实像素，不是目测。

### 5.4 为什么删掉头部辉光环

首版在脸上画一圈会呼吸的椭圆光环，想用它提示"碰撞体在这里"。删掉有三个理由：

1. **它必然看起来是歪的**。椭圆由 478 个 landmark 的包围盒拟合，为了让碰撞体包住整张脸，
   代码里带了放大系数（`rx*1.16`、`ry*1.24`）。光环沿这个椭圆描边，就永远比真实脸大一圈，
   在侧脸或俯仰时会明显偏向一侧 —— 这不是对齐 bug，是拟合策略的必然结果。
2. **它改变了脸部观感**，与"人保持原样"的原则冲突：亮环叠加在肤色上会让下颌线凭空变亮。
3. **它承担的信息是冗余的**。碰撞本来就由粒子自身的反弹溅射表达得很清楚
   （雨滴撞脸后转为下滑的水痕，火花碰到椭圆会弹开），不需要再描一圈边。

同时把背景暗化的过渡加宽（`0.92→1.30` 改为 `0.98→1.60`）：
椭圆比脸大一圈，硬过渡会把暗化边界暴露在脸颊外侧，看起来像一张罩住脸的"面膜"。

### 5.5 让雨"更强更持久"的三个参数

雨势弱的根因不在雨的颜色，而在**密度**和**包络**：

| 改动 | 前 | 后 | 理由 |
| --- | --- | --- | --- |
| 雨槽位占比 | 7.5~9.0% | **20%** | 雨的"强"首先是密度。雨是每滴一条线段（2 顶点），比火花的点精灵+拖尾便宜得多，加量几乎免费 |
| 拖尾长度 | `7.0 + speed*0.014` | `11.0 + speed*0.022` | 短雨丝即使数量多也像下小雪，长雨丝才是"下大雨"的直观信号 |
| 景深起伏 | `0.22 + seed*0.78` | `0.34 + seed*0.66` | 抬高低谷让远处雨丝也看得见，整片雨才密实而不是稀稀拉拉 |
| 整体亮度 | `×0.42` | `×0.60` | 雨是这场互动的主角之一，不该只是背景噪点 |

包络上的两个改动影响更大：

1. **雨滴不再被瞬杀**。旧实现在 `uRainIntensity` 下降时直接 `life = 0`，
   一松口雨就整片瞬间消失，完全没有"雨渐渐停"的过程。改为**只控制出生数**，
   已存在的雨滴自然落出画面。
2. **非对称包络**。雨量不再直接透传瞬时笑意，而是走包络：
   起雨半衰 **0.18s**（要跟得上表情），收雨半衰 **1.35s**（雨幕慢慢收）。

实测衰减曲线（满雨稳态 → 松口）：

| 时间 | 0.25s | 0.50s | 0.75s | 1.00s | 1.25s |
| --- | --- | --- | --- | --- | --- |
| 剩余雨量 | 69% | 18% | 7% | 7% | 1% |

即松口后有约 **0.5s 的可见雨尾**，而不是一帧断掉。

```bash
# 任意静态服务器均可，必须走 http(s) 而非 file://（ES module + 摄像头权限）
npx serve .
# 或
python -m http.server 8080
```

> 摄像头只在 **HTTPS / localhost** 下可用；`file://` 打开会同时卡在模块加载和权限上。

## 7. 目录结构

```
index.html            页面与 UI 骨架（importmap 引入 MediaPipe ESM）
src/
  main.js             主循环编排、连击状态机、镜头震动（镜像 + cover 的唯一真相）
  shaders.js          GLSL ES 3.00 着色器集（模拟 / 火花 / 雨 / 辉光 / 合成）
  glRenderer.js       WebGL2 渲染器（ping-pong FBO + MRT + 质量档位）
  legacyRenderer.js   Canvas2D 降级渲染器（接口与 GLRenderer 一致）
  faceTracker.js      FaceLandmarker 封装（GPU→CPU 降级、静止帧跳过推理）
  expressionFSM.js    表情状态机（基线归一化 + 平滑 + 迟滞 + 连续帧确认）
  collision.js        头部椭圆拟合与 CPU 侧弹性碰撞（降级路径用）
  particles.js        SoA 粒子池 + 雨场 + 预烘焙 sprite（降级路径用）
  perf.js             FPS → 质量档位的自动降级
  ui.js               DOM 映射层（节流写入、飘心节点池）
  styles.css          样式与手机端响应式
docs/plan.md          执行计划
```

## 8. 已知边界（Edge Cases）

- 未授权摄像头 / 非安全上下文 / 模型 CDN 不可达：均有明确降级文案，不白屏。
- 多人同框：只追踪 1 张脸（`numFaces: 1`），避免特效归属混乱与算力翻倍。
- 快速转头或强逆光：网格抖动时头部椭圆做 0.4 系数插值，碰撞体不会瞬移。
- 极端大笑导致的连续 burst：有 380ms 冷却与 520ms 持续间隔，避免粒子瞬时打满池。
- WebGL context 丢失：已实现恢复逻辑。

## 9. Vibecoding 复盘

**最大的性能陷阱**：AI 首版把粒子物理写成 **CPU 逐帧 JS 循环**遍历数组更新位置与碰撞，
粒子一过几千帧率就崩，且坚持「先跑通再优化」拒绝动架构。

**更隐蔽的是碰撞判据幻觉**：AI 用「当前在椭圆内就反弹」，导致在嘴部（碰撞体内部）
出生的烟花一出即被弹到边缘、堆成一圈光球；换成「速度朝内就反弹」又堆成一个碗。

**架构调整**：强制把整个粒子系统迁到 GPU —— 状态打包进两张浮点纹理，
在 fragment shader 里用 ping-pong FBO 做模拟，CPU 彻底退出物理计算；
碰撞改用「**上一帧在椭圆外、这一帧在椭圆内**」的边界穿越判据，
让内部出生的粒子自由掠过脸部，只有从外部落回时才真正撞击反弹。

**纠偏 Prompt**：

> 不要用 JS 循环更新粒子，把位置/速度/寿命打包进浮点纹理，物理模拟全部放进 fragment shader
> 用 ping-pong FBO 做；碰撞用上一帧在椭圆外、这一帧在椭圆内的边界穿越判据，
> 不要用「当前在内部就反弹」。逐条给出修改后每帧的 CPU 工作量与堆分配次数。
